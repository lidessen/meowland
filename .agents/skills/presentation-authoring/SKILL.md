# Presentation authoring and continuous revision

Let agents and people co-create around a runnable work. The current delivery is browser presentations; PPT export is a later capability, so do not limit interactions to an exportable supported set, and do not promise an existing PPT/PDF converter.

First read the work's existing README, entry point and asset notes. New works start from the [MDX authoring example](../../../examples/presentation/README.md), with the [Meowslides README](../../../packages/meowslides/README.md) and public exports as the source of truth; regular authors maintain `slides.mdx`, assets and any necessary MeowJSX interactive components, while the host and build are handled by the tooling. For a complete interactive explainer see the [image-loading work](../../../examples/image-loading/README.md); do not treat dedicated animation, asset production and browser fixtures as the starting task of every script.

MDX is trusted local code and supports imports, expressions and component execution; arbitrary text uploaded, generated by a model or fetched externally must be reviewed first and is not executed as MDX by default. Leave blank lines around top-level `---` page breaks; page metadata and reveals follow the actual implementation; complex interactions import MeowJSX components explicitly and do not assume React hooks compatibility. Do not treat historical design drafts as implemented capability.

## Choose the layout starting from content regions

First read [presentation content layouts](../../../packages/meowslides/PRESENTATION-LAYOUTS.md), divide regions by the relationship between the point, the evidence and the action,
then place titles, images and body text. Prefer PresentationLayout's header/footer slots and equal columns such as `1 | 2 | 3`,
or the named column ratios single/equal/wide-start/wide-end; inside a region continue with Stack/Grid. Title, image-and-text, comparison, numbers, process, quote and summary are composition recipes.
Use PresentationList's items for short points; when order matters use `as="ol"` and keep native semantics such as start/reversed.
Lists use the presentation body token (28px by default in the standard theme); do not fill three columns via size/density or automatic shrinking; long content is first trimmed, split across slides or moved to another region.

Prefer PresentationImage for body images, defaulting to 16:9, contain and center; the caption takes its natural height and reuses ImagePreview's failure feedback.
`fill` requires a finite parent such as PresentationLayout body or LayoutItem grow, and the image uses the space left after the caption; when the parent height is uncertain use a numeric ratio.
Prefer showing text images in full; use explicit cover only when a photo genuinely must fill the area, and check the nine-point position and subject cropping; with different aspect ratios you cannot guarantee both intact edges and a filled region.
Placeholders and real images use the same ratio container; after replacement check actual cropping, long captions and descriptions. Column ratios inside the logical canvas do not reflow for narrow host screens;
Presentation scales the whole canvas. When a long title and the final step do not fit, first trim, split the slide or change the region; do not deliver by automatic shrinking or hiding overflow.
When a title genuinely needs typographic emphasis, use PresentationText editorial/marker, and keep body text plain; it is still real selectable text,
so do not describe the native contenteditable seam as an editor. Static composition and content clarity must hold first, then choose the necessary transition entrance.
Set the background default for the whole show first, then override it completely per slide; foreground refers to text lightness, so with the base color and overlay in place, actually check that the slide stays readable after an image fails, and keep body text and alt for key images.

## Run early, then change together

A short brief only needs the audience, what should change after viewing, the duration, the core claim, evidence/uncertainty and hard constraints; use existing material as well. Write changeable assumptions where inference is possible, and only ask questions that change direction. State each scene's purpose in one sentence; for interactions, make clear which variable the audience changes and which result they see.

Try rough content together with the first set of fonts, colors and typography. If something runnable exists, look at it first; aim to cover the opening and the hardest interaction in the first round, but do not wait for them to be finished simultaneously, and do not wait for the full draft, outline approval or complete assets. Images, video and music may start as explicit placeholders; when comparison is needed, do a small real A/B so people can see the difference and choose.

Each round choose the most important 1–3 issues based on the preview; changing the script, visuals, assets and interaction in the same round is allowed, then look at the whole show again for narrative, density and pacing, without permanently freezing one layer. If the person has chosen layout B and only asks to change the conclusion and image, keep that structure and patch just the corresponding text and asset locally instead of regenerating the whole show.

Keep only the necessary brief, work source, assets/sources and current feedback; merging documents is allowed, and there is no mandatory four-file structure, scaffold or ledger. Ordinary Git checkpoints and local diffs are used for comparison/rollback; actual commits still follow this run's authorization.

## Courseware scenarios

Real courseware entry points and teacher-operation examples are in [Sunshine for all / Welcome](../../../examples/sunshine-welcome/README.md); its textbook edition and classroom activities belong only to that work and are not fixed content or structure for all courseware.

Courseware additionally states the target students, existing knowledge and this lesson's learning goals; goal descriptions state what students can explain, apply or judge and on what basis. Record subject, grade, volume, textbook edition and unit; do not guess the table of contents from city and grade alone. First verify user material or traceable textbooks, texts and reference courseware, and state whether what you actually read is a table of contents, a search snippet, a partial preview or the full text. Distinguish textbook original text, others' explanations and your own adaptation; do not invent missing body text, page numbers or standard answers. If the user only asks for references or the text, first deliver sources, edition correspondence and points still to verify; do not expand on your own into a complete unit deliverable.

Follow the shared iteration: try one verified explanation point and key question or exercise together with fonts, colors, images and interaction into a previewable segment; the rest of the material may continue to be verified or explicitly kept as placeholders. Adjust the pacing of explanation, thinking or answering, exercises and feedback according to preview feedback; do not wait for the whole lesson script to be final, and do not force every slide into fixed lesson-plan sections.

For each teaching segment first state "what students do, what observable output remains, on what basis, and how they get feedback", then decide pages and presentation order; one sentence is enough, and a lesson-plan table or complete outline first is not required. Outputs may be spoken reasoning, annotation or manipulation; they do not all need to become on-screen input and data collection. More material does not mean more goals for one lesson period. Try one key segment first, adjust tasks, wording, density and scaffolds based on the real preview, and keep the shared iteration.

Teachers use the existing step / `Reveal` to control the necessary order; by default do not let media end or a timer automatically reveal. Decide visibility timing separately for the question, hint, reference answer and evidence marker; keep the original reading material available, and do not let titles, captions or sentence frames leak the conclusion students should derive. When scaffolds are needed, retreat from complete expression to keywords and sentence frames and then to independent expression, allow asking for help again, and do not make every layer a required step. Reveal's `at` reveals cumulatively by step; local repeated showing/hiding is wired into `when` by the work's ordinary signals, which does not mean a fill-in-the-blank exercise or scaffold-level component already exists. Removing a scaffold may also simply mean the next task no longer offers it.

Teaching options inside the canvas expand directly into clickable text, option blocks or cards so students see all candidates at a glance; do not hide candidates in a dropdown select. Buttons follow this presentation's fonts, sizes, colors and shapes; do not drop an ordinary application form skin into the PPT canvas; keep native semantics, keyboard, visible focus and non-color-only selection feedback. Make hint/reference actions visually and positionally distinct from answer options. The surrounding player's catalog belongs to navigation and is not removed because of the classroom option principle. See [Protecting pandas](../../../examples/protecting-pandas/README.md) for a real example; it is not a new teaching component API.

For support areas that toggle repeatedly use the shared `Reveal when={shown}`, choosing one of `when` or `at`, keeping a stable reading area and action position; do not copy hiding, focus and activity-permission wiring into the work. Also check the default state, each support opened alone, all opened and all retracted, not only the fully expanded state. Prefer `slideClassName` for content styles to avoid root descendant selectors affecting the surrounding player; when capacity is insufficient, adjust to a reasonable composition based on shared diagnostics, and do not hide the problem with opacity, smaller text or per-slide pixel nudges. State which segment a reference example corresponds to, so a fixed example does not look like automatic feedback for the current choice.

Explain separately what page forward/back, phase change and redo keep or reset; going back does not automatically erase answers. Give feedback on open questions by evidence, expression and discussable reasoning; reference examples are not the single answer, and completing a matching exercise does not mean students can explain or evaluate. Leave changeable time budgets for independent thinking, peer expression and whole-class sharing, and arrange an output for every student so presentation content and a few reports do not fill the whole class.

When authoring courseware read [teaching segments and adaptation cases](../../../packages/meowslides/PRESENTATION-LAYOUTS.md#teaching-segments-and-retractable-scaffolds), and reuse a suitable small composition first. The running case is designated by the user as "Grade 8 Volume 1 Unit 5 Wild animals — Reading: Protecting pandas", organized along growth information, problems/consequences, protection measures and evidence-based personal action; mark classroom activities and sentence frames as teaching adaptation, do not fabricate unverified textbook sentences, and do not infer edition or page numbers. It does not replace the other work Sunshine for all / Welcome. The preview replays this segment's key states — unprompted, hint, reference explanation, scaffold retracted/restored, forward/back and explicit redo — and checks keyboard, assistive-technology hiding and answer leakage; do not substitute a fully expanded screenshot. When new teaching capabilities are needed, read [research digestion and capability boundaries](../../../docs/designs/2026-10-18-classroom-authoring.md), separating candidate requirements from implemented APIs, and do not expand the whole teaching platform at once.

Citations and asset sources follow the asset conventions later in this document; textbooks additionally record edition, volume and verifiable page/lesson names. Reference courseware is used to compare organization and explanation methods; do not treat source attribution as authorization to copy it wholesale; use text citations, images and audio/video according to actual authorization, and generated assets do not masquerade as the text, textbook illustrations or teaching factual evidence.

## Keep feedback and state reviewable

Locate feedback with a stable `slideId`, a distinguishable version for the current round and the relevant step/fixture, and add a sentence on "what does not hold and what should change"; record sizes only when relevant. When someone says "slide 3", resolve it to the id in the current preview. Reordering does not change ids; after steps change meaning, slides split or pages are deleted, re-locate old feedback and do not claim re-verification passed just because the old step numbers are still valid. Versions may reference existing screenshots or working copies; no version database is needed.

Handle position, experiment input and run permission separately: all navigation writes the same position Signal; each presentation creates ordinary experiment signals once and slides only reference them, so choices persist across slides and summaries stay in sync without values leaking between works. Steps are directly presentable state; going back does not undo an independent experiment; the experiment reset is provided explicitly by the author. When jumping back to a source requires restoring the original step, the work only needs to save an ordinary position value, without extending the navigation history system.

After source changes, use Meowslides dev's rebuild/refresh, or restart and reload following the actual Meowbook review flow, and confirm it is a new build. Record the few inputs and positions related to the feedback before the change, and replay after it; when it repeats, form an ordinary typed fixture. Reload does not guarantee session restoration; do not call it state-preserving HMR, and temporary parameters must not quietly become work defaults.

## Placeholders, real assets and evidence

Placeholders state their purpose, container ratio, fit/crop and text avoidance; videos additionally record the poster/explanation point, music its purpose, interactions their variables and results. When replacing, keep the container and reference relationships first, then check actual cropping, color, text and behavior; if the meaning changes, update the narrative together and do not force old copy to stay.

Lightweight source notes keep the original source, purpose, authorization, processed or generated version and necessary notices, so old references can be rolled back. Generated images can help expression but must not masquerade as real measurements, screenshots or factual evidence; numbers, image-quality comparisons and loading recordings must correspond to real files and conditions, and simplified formulas state units and omitted factors.

Images provide suitable alt text; decorative images may have empty alt; videos provide captions or a text alternative; audio has a visible name and native controls. Asset generation, upload and persistence are handled by actual tooling or the host; do not add an asset registry for authoring. Choose media according to content needs and do not stuff in music to show capability.

## Preview, operation and delivery

Regular works preview and deliver with Meowslides dev/build; when component review is needed, connect the same page source as a Meowbook story rather than requiring story maintenance from the start. Discover scenes, checks, previews and captures following the [Meowbook contract](../../../packages/meowbook/README.md) and [visual evidence](../ui-development/references/visual-checks.md); do not duplicate a second set of engineering commands. Review/background instances pass `active=false` from the first mount; during actual foreground operation the host opens permission, and document visibility alone is not a judgment. Each preview and official entry creates an independent session to avoid module-level singletons.

Custom animation and media respond to activity permission and register cleanup; structural presence does not mean playback is allowed. Observe normal animation, reduced motion, keyboard, cross-slide/back, pause, background and exit according to the work's actual capabilities; steps do not remount the whole slide, and interaction keys are not stolen by page navigation. Media ending does not advance the narrative, and restoring time does not mean restoring sound. `ready`, font waiting, a poster or a successful screenshot does not prove all resources/animations are ready; wait for the explicit fixture condition, then look at the actual original image and operation.

The official browser entry reuses the work's JSX, theme and assets, independent of the Meowbook gallery/dev server. Deliver a runnable Web artifact, editable source and assets, dependency/lock files, sources/notices, remaining placeholders and accurate launch instructions; check whether notes and author material should enter the audience bundle. Carry fonts, images, media, posters and captions explicitly; a runtime string URL does not mean the resource is bundled.

Shut down the dev server and cold-start from the actual delivery entry to verify paths, fonts, media and interaction; offline, double-click-file or deploy-subdirectory support is accepted separately per the work's convention and is not assumed by default. The exit condition is that narrative/evidence and the chosen visuals hold, local revisions have been re-reviewed, target sizes are readable, the controls/cleanup actually used work end to end, and asset status and launch instructions are accurate. On handoff, distinguish implementation, actual observation, unverified parts and user acceptance; do not substitute a successful screenshot or build for completion, and do not automatically publish, push or deploy.
