# Component catalog

Use this catalog to choose Meowtail components and decide which shared capabilities to build next.
It owns the component grouping, purpose, selection reasons, and target decisions. The public
[component exports](src/components/index.ts) and [chat exports](src/chat/index.ts) define what the
source actually provides; their types and the linked usage documents define the API.

Meowtail serves application interfaces, including Agent conversations and workspaces. Components
own reusable structure and interaction, the standard theme owns their appearance, and hosts own
business facts, execution, permissions, networking, uploads, and persistence. A concrete task can
justify a target before a consumer has been implemented. A name in another toolkit is insufficient.

## Reading the catalog

The current list covers all 107 component values in `src/components/index.ts` and all 22 in
`src/chat/index.ts`, checked on 2026-10-28. Each value belongs to one family below. Related public
parts stay beside their composition; each member's role is stated. CSS contract parts, types,
helpers, icon assets, and runtime installation APIs do not count as additional components.

Current means exported by the source. Release and acceptance status remain in the
[package README](README.md), [root README](../../README.md), and their linked receipts. Importability
does not establish that every scenario has passed acceptance or that the npm release contains it.
The [Agent scenario index](#agent-scenario-index) points back to the same families rather than
maintaining another component inventory.

Start with the complete composition for the task: a content page, modal, navigation list, or
Assistant. Use its public parts when the default composition cannot express the task. The reasons
below explain those choices; they do not rank low-level parts as less supported.

### Naming and discoverability

Prefer widely used component names when their familiar behavior matches the contract. This helps
developers and Agents recognize a component without learning a separate vocabulary. Keep a more
specific name when a familiar alternative would imply different behavior. Existing names such as
Button, Checkbox, Tabs, Popover, Toolbar, and SegmentedControl already serve that purpose.

The family labels below use familiar task terms for searching; the code names beside them are the
actual exports. For example, search for a radio group and import the current `ChoiceGroup`.
Proposed replacements belong in the naming review below until an API change is implemented.

## Component layers

The families below group components by task. Independently, every component sits in one layer,
which states what it owns and what it may build on. Layers describe responsibility, not support:
each layer is equally public. A component builds only on components in its own or a lower layer;
today's source imports hold to that.

| Layer           | Owns                                                                                                                                        | Members                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L0 Elements     | The modern HTML layer: native semantics, platform behavior, accessible wiring and named parts for one element-level job.                    | Layout: `Stack`, `Inline`, `Grid`, `LayoutItem`, `Container`, `PageFrame`, `AspectRatio`, `Separator`, `Section`, `DetailSection`. Text: `Text`, `Prose`, `Link`, `ShortcutKeys`, `PathLabel`. Actions: `Button`, `IconButton`, `AddButton`. Forms: `Field`, `FieldGroup`, `Input`, `Textarea`, `NumberInput`, `Checkbox`, `Switch`, `Slider`, `Select`, `ChoiceGroup`, `SegmentedControl`. Layers: `Dialog` and its parts, `Popover`, `Tooltip`, `Disclosure`. Surfaces: `Card` and its parts. Marks: `Progress`, `Spinner`, `Skeleton`, `StatusDot`, `StateDot`, `Badge`, `Tag`, `Pill`, `Avatar`. |
| L1 Patterns     | A reusable interaction or record pattern composed from elements, with the pattern's own behavior (keyboard model, selection, fit, sorting). | `Tabs`, `Accordion`, `Toolbar`, `ActionRow`, `ActionRail`, `Menu`, `MenuButton`, `ContextMenu`, `HoverCard`, `Modal`, `Drawer`, `RiskConfirmation`, `ChoiceSelect`, `SearchInput`, `NavList`, `NavItem`, `Breadcrumb`, `ListGroup`, `ListRow`, `Item`, `DescriptionList`, `DescriptionItem`, `Timeline`, `TimelineItem`, `Table`, `ResourceCard`, `ResourceLink`, `MetaRow`, `Alert`, `EmptyState`, `Status`, `Toast`, `TextShimmer`, `SkeletonBoundary`, `ImagePreview`, `ImageLightbox`.                                                                                                           |

### Element contract

An L0 element is what HTML would offer if it were designed for application interfaces today. It
keeps these rules, and patterns and compositions inherit them by building on it:

- **Native first.** Build on the element or platform API that already carries the semantics
  (`button`, `input`, `fieldset`, `dialog`, `details`, `popover`). Add only what the platform lacks,
  such as a keyboard model or anchored positioning; do not reimplement what it provides.
- **Wiring is derived.** Ids, label, description and error associations, and heading levels come
  from the component tree. `id`, `htmlFor` and `as` exist to override, never because the caller
  must supply them.
- **Finite semantic options.** Props choose among named roles (`gap`, `tone`, `size`), not free
  CSS values, so the same choice reads the same in every theme.
- **Parts, not looks.** The component names its parts and options in `meta`; the theme paints them.
  It looks finished without a `className`.
- **No host facts.** State, data, permissions and side effects arrive through props, children and
  events.

When a pattern or composition needs something an element cannot express, add it to the element
rather than working around it one layer up. A new component states its layer in its family row
reason or review before it is added.

## Targets and open candidates

These are capability decisions for the intended toolkit. They distinguish a missing interaction from
a new name for something already available. Proposed names below are descriptive; selection does
not commit to a final export, API, implementation date, or release. It does not authorize runtime
implementation in a documentation change.

- **Selected target:** the task belongs in Meowtail's intended surface and merits shared support.
  Implementation may extend an existing family instead of adding a component.
- **Investigate:** a meaningful task exists, but its missing behavior or contract needs clarification.
- **Deferred:** keep the possibility visible and revisit on the stated evidence.
- **Outside Meowtail:** responsibility belongs to a host, another package, or a consumer template.

The task examples below state intended usage unless an observed repository consumer is explicitly
identified. A local call site is useful evidence, but is not a prerequisite for selecting a coherent
cross-application interaction. Searching a large set of models, projects, or users and committing
one valid option is already covered by the current searchable picker. Prefer that family; the
editable-combobox question below requires a distinct input task.

## Reference and decision basis

[shadcn/ui](https://ui.shadcn.com/docs/components) supplies useful comparisons for complete fields,
search/selection interactions, overlays, and command composition. Its
[AI Elements](https://ui.shadcn.com/docs/ai-elements) also provides an Agent-oriented comparison.
[MyGo UI](https://mygo.egoist.dev/docs/ui) makes behavior gaps visible: its
[combobox](https://mygo.egoist.dev/docs/ui/combobox),
[autocomplete](https://mygo.egoist.dev/docs/ui/autocomplete), and
[token field](https://mygo.egoist.dev/docs/ui/token-field) distinguish constrained, arbitrary-text,
and multiple-value input. Its [outline](https://mygo.egoist.dev/docs/ui/outline) and
[Markdown](https://mygo.egoist.dev/docs/ui/markdown) are useful references for hierarchy and streaming
reading. Apple's [SwiftUI container guidance](https://developer.apple.com/documentation/swiftui/picking-container-views-for-your-content)
provides a comparison for semantic containers. These are reference lenses; the tasks and boundaries
above decide what Meowtail selects.

[Pele](https://github.com/obsidianmd/pele) is the selected Mermaid renderer. It is an independent
Mermaid-to-SVG implementation, not a Mermaid.js wrapper; its render/mount APIs and CSS-variable theme
are integration inputs. Its [security guidance](https://pele.run/security) informs safe rendering
and host resource policies.
[shadcn Chart](https://ui.shadcn.com/docs/components/base/chart) and
[Swift Charts](https://developer.apple.com/documentation/charts) inform quantitative display.
The Chart engine and its full feature set remain undecided. Selecting Pele does not establish
implementation or acceptance of the Mermaid target.

The local evidence is the public exports, linked component sources,
[Assistant contract](ASSISTANT.md), and [Agent composition guide](AGENT-COMPONENTS.md).
The [authoring catalog](../../docs/designs/2026-10-21-authoring-component-catalog.md) records the earlier
authoring-only plan and its original sequence; it is historical input, not the current inventory.
The current list deliberately covers Agent reading and work as well as docs and content pages.

## Maintaining this list

Update the affected family in the same change that adds/removes a public component or materially
changes its intended use. Keep every public member's purpose and selection reason visible; put
compound parts beside their composition rather than adding duplicate task-specific entries.
Update the scenario index when a reading or interaction gap changes.

For a new target, state the user task, what the existing composition fails to provide, and the
appropriate owner. A clear intended scenario can justify selection before a local consumer exists;
claim an observed consumer only with a source link. Decide mechanisms through the repository's
existing design review process. Move implemented capability into the current family when the source
exports it, and report acceptance and publishing through the existing receipts. Extend a current
family when it already owns the behavior.

Reconsider a target when the task disappears or an existing family covers it. Review an existing
export with no supported purpose instead of treating its presence as permanent justification;
removal still needs a deliberate API and consumer change. This catalog does not automatically
retire existing components.

When changing the inventory, compare the component and chat export names with this list. The
2026-10-22 reconciliation covers all 126 current values once; no generated registry, duplicate
metadata schema, or new CI gate is needed to maintain the human selection reasons.
